# Асинхронный процессинг платежей

Решение [тестового задания](задание.pdf): два HTTP-эндпоинта, эмуляция шлюза,
transactional outbox, RabbitMQ, webhook, три попытки и DLQ.
Разбор выполнен до кода; первоначальный [план](PLAN.md) сохранён отдельным коммитом.

## Запуск

Нужны Docker и Docker Compose. Из корня проекта в PowerShell:

```powershell
Copy-Item .env.example .env
docker compose up -d --build --wait
```

В Bash первый шаг: `cp .env.example .env`. В `.env` можно изменить `API_KEY`
(минимум 16 символов). Значение из примера предназначено для локального запуска.
Миграции применяет API до начала приёма запросов; consumer запускается после
готовности API и RabbitMQ. Дополнительных ручных шагов с БД и очередями нет.

| Сервис | Адрес на хосте |
| --- | --- |
| API | `http://localhost:58000` |
| RabbitMQ Management | `http://localhost:55673`, логин/пароль `payments` / `payments` |
| PostgreSQL | `localhost:55432`, БД/логин/пароль `payments` |
| AMQP | `localhost:55672` |

Порты привязаны к loopback. Их можно изменить через `API_PORT`, `POSTGRES_PORT`,
`RABBITMQ_PORT`, `RABBITMQ_UI_PORT` в `.env`. Между контейнерами используются
внутренние адреса. Для остановки с сохранением данных: `docker compose down`.

## Проверка

Полный путь с настоящим HTTP-получателем webhook:

```powershell
docker compose exec api python tests/smoke.py
```

Скрипт запускает временный HTTP-получатель внутри сети Compose, создаёт платёж,
дожидается уведомления, сверяет результат с GET, проверяет повтор запроса и
конфликт ключа. Ожидаемый вывод: `PASS: API -> outbox -> RabbitMQ -> gateway -> HTTP webhook`.
Платёж остаётся в БД для просмотра. Результат шлюза может быть `succeeded` или `failed`.

Интеграционные тесты, проверка миграции и статические проверки:

```powershell
docker compose exec -e TEST_DATABASE_URL=postgresql+asyncpg://payments:payments@postgres:5432/payments -e TEST_RABBITMQ_URL=amqp://payments:payments@rabbitmq:5672/ api python -m pytest -q
docker compose exec api alembic check
docker compose exec api ruff check app migrations tests
docker compose exec api ruff format --check app migrations tests
```

Тесты создают отдельные случайные схемы PostgreSQL и очереди RabbitMQ, затем
удаляют только свои ресурсы. Данные приложения не очищаются. Модели в тестовых
схемах создаются через SQLAlchemy; саму миграцию отдельно проверяем чистым
Compose-запуском и `alembic check`.

Для локальной разработки: Python 3.12+, `python -m venv .venv`, активация окружения,
`python -m pip install -r requirements.lock`, `docker compose up -d postgres rabbitmq`.
API запускается командой `uvicorn app.api:create_app --factory`, consumer —
`python -m app.worker`. Для миграции задайте `DATABASE_URL` из `.env` в окружении
и выполните `alembic upgrade head`. Локальные тесты: `python -m pytest -q`.

## HTTP-контракт

Все маршруты, включая `/docs` и `/openapi.json`, требуют `X-API-Key`.
Интерактивная форма входа для Swagger не добавлялась: спецификацию можно получить
авторизованным HTTP-запросом. Пример для PowerShell:

```powershell
$headers = @{
    'X-API-Key' = 'local-development-key-change-me'
    'Idempotency-Key' = 'order-42'
}
$body = @{
    amount = '125.50'
    currency = 'RUB'
    description = 'Order 42'
    metadata = @{ order_id = 42 }
    webhook_url = 'https://your-server.example/payments/webhook'
} | ConvertTo-Json
$payment = Invoke-RestMethod -Method Post -Uri http://localhost:58000/api/v1/payments -Headers $headers -ContentType 'application/json' -Body $body
$payment
Invoke-RestMethod -Uri "http://localhost:58000/api/v1/payments/$($payment.payment_id)" -Headers $headers
```

Адрес webhook в примере нужно заменить на свой. Для проверки без внешнего сервера
используйте smoke-скрипт выше. `localhost` в webhook означает контейнер consumer,
а не машину пользователя.

`POST /api/v1/payments` возвращает `202`:

```json
{
  "payment_id": "6ea83cfa-9e9c-42cc-9beb-350349e16b09",
  "status": "pending",
  "created_at": "2026-10-23T12:00:00Z"
}
```

`GET /api/v1/payments/{payment_id}` дополнительно возвращает `amount`, `currency`,
`description`, `metadata`, `webhook_url`, `processed_at`. До завершения
`processed_at = null`. Служебные поля попыток и хеш запроса в API не выдаются.

- Сумма: строго больше нуля, `NUMERIC(18,2)`, максимум `9999999999999999.99`.
  Более двух значащих знаков после точки отвергаются, округления нет. В ответах
  сумма строкой; в запросах тоже рекомендуется строка.
- Валюта: `RUB`, `USD`, `EUR`. Описание: 1–1000 символов.
- Метаданные: JSON-объект, по умолчанию `{}`. Неизвестные поля запроса запрещены.
- `Idempotency-Key`: 1–200 печатных ASCII-символов без пробелов.
- Webhook: HTTP/HTTPS URL, до 2048 символов.
- Ошибки: `401` — ключ API; `404` — неизвестный платёж; `409` — конфликт
  идемпотентности; `422` — неверный запрос; `503` — ошибка доступа/записи в БД.
- Время хранится и передаётся с часовым поясом, в UTC.

Webhook — HTTP POST с таким телом:

```json
{
  "payment_id": "6ea83cfa-9e9c-42cc-9beb-350349e16b09",
  "amount": "125.50",
  "currency": "RUB",
  "status": "succeeded",
  "processed_at": "2026-10-23T12:00:03+00:00"
}
```

Любой `2xx` подтверждает доставку. Остальные статусы, сетевые ошибки и таймаут
приводят к повтору. Общий срок одного HTTP-запроса ограничен пятью секундами,
перенаправления отключены. Получатель должен распознавать дубликаты по `payment_id`.

## Архитектура и ключевые решения

```text
POST -> PostgreSQL: payments + outbox (одна транзакция)
                         |
                  relay в consumer
                         v
                  RabbitMQ payments.new
                         |
          обработчик: эмуляция -> commit результата -> webhook
                         |
             успех: commit + ACK
             ошибка: commit следующей outbox-записи + ACK
                         |
                попытка 2 / попытка 3 / payments.dlq
```

1. **Одна БД, две таблицы, без дополнительных слоёв.** FastAPI использует
   SQLAlchemy напрямую. Уникальный индекс и `INSERT ... ON CONFLICT` защищают от
   конкурентных дублей. Нормализованное тело сравнивается по SHA-256; другой
   запрос с тем же ключом не подменяет уже принятый платёж.
2. **Outbox охватывает и повторы.** Поля `available_at`, `published_at`,
   `handled_at` задают отложенную публикацию и квитанцию обработки. Закрытие
   попытки и создание следующего события/DLQ атомарны. Отдельный scheduler,
   retry-плагин RabbitMQ и третья таблица не нужны.
3. **Подтверждения в правильном порядке.** Relay использует persistent messages,
   publisher confirms и mandatory routing; только затем отмечает публикацию.
   Consumer подтверждает сообщение после коммита. Потеря подтверждения допускает
   повтор, который распознаётся по outbox ID. Очереди durable quorum; повреждённые
   сообщения и неизвестные event ID направляются через DLX в DLQ.
4. **Результат платежа отделён от уведомления.** Исход шлюза фиксируется до HTTP.
   Отказ webhook не меняет `succeeded` на `failed` и не повторяет шлюз.
   Строковые блокировки ограничивают конкурирующую обработку одного события.
5. **Один consumer и один процесс relay.** Prefetch равен 1. Во время эмуляции и
   HTTP удерживаются короткие транзакции с блокировками: 2–5 секунд и максимум
   5 секунд соответственно. Это сознательный обмен пропускной способности
   на простоту для масштаба задания. HTTP-клиент и пул БД переиспользуются.

Основные модули: `api.py` — HTTP и идемпотентность; `db.py` — схема БД;
`processing.py` — обработка и смена попыток; `worker.py` — RabbitMQ и relay;
`schemas.py` и `config.py` — контракты и настройки. Все находятся в `app/`.

## Вопросы и принятые допущения

| Неопределённость ТЗ | Принятый контракт |
| --- | --- |
| Повтор ключа: то же или другое тело? | То же нормализованное тело: `202`, прежний ID и текущий статус. Другое: `409`. Ключ глобальный и без TTL, поскольку клиентов и срока хранения в ТЗ нет. |
| 10% ошибок шлюза: отказ или временный сбой? | Окончательный `failed`; о нём тоже отправляется webhook. Иначе повторы превращали бы отказы в успехи. |
| Три попытки или три повтора? | Всего три попытки, задержки перед второй и третьей — 1 и 2 секунды, плюс до 250 мс polling и время ожидания очереди. |
| Что передавать webhook и когда считать доставленным? | Контракт выше; любой `2xx`, пять секунд на запрос. Это явно выбранный контракт, отсутствующий в PDF. |
| Гарантируется ли отсутствие дублей? | Нет: доставка как минимум один раз. Exactly-once внешнего HTTP без участия получателя не обещается. |
| Какие ограничения у полей? | Положительная сумма с двумя десятичными знаками, обязательные описание и URL, необязательный JSON-объект metadata. Пределы указаны выше. |
| Что означает «один consumer»? | Один экземпляр, один обработчик всего процесса; relay — фоновая задача этого процесса. Четыре сервиса Compose соответствуют ТЗ. |

Три попытки относятся к обработке с сохранённым результатом ошибки. Если БД
недоступна, consumer удерживает исходное сообщение без ACK и ждёт восстановления
с паузами 1, 2, 4, 8, затем 10 секунд. Relay при сбое сохраняет запись и повторяет
публикацию. Инфраструктурная недоступность не расходует прикладные попытки.
При аварии процесса до коммита возможна дополнительная физическая попытка HTTP.
У RabbitMQ остаётся собственный защитный лимит повторных аварийных доставок;
его исчерпание также ведёт в DLQ.

## Что проверено

На 23 октября 2026 года:

- 22 теста прошли на Windows/Python 3.12 и внутри Linux-контейнера.
- Конкурентные запросы с одним ключом создают один платёж и одно событие.
- Конфликт ключа, нормализация суммы, валидация, авторизация, `404`.
- Ошибка вставки outbox откатывает платёж; ошибка вставки retry не закрывает
  исходное событие.
- Успех и отказ шлюза, конкурентный дубликат сообщения, потеря HTTP-ответа,
  возобновление после прерывания между коммитом платежа и webhook.
- Три неудачных отправки, интервалы повторов, сохранение результата платежа.
- Настоящий RabbitMQ: unroutable publish не отмечается отправленным;
  восстановление маршрута, отложенная публикация, повтор после потери коммита,
  полный consumer/retry/DLQ, повреждённое сообщение, временная ошибка БД.
- Чистый Compose-запуск с новыми томами; миграции без ручной подготовки;
  `alembic check` не обнаруживает расхождений с моделями.
- Smoke-проверка с реальной эмуляцией и настоящим HTTP-webhook.
- Остановка настоящего RabbitMQ: API вернул `202`, событие осталось
  неопубликованным в БД. После запуска брокера платёж обработался без ручного
  вмешательства; недоступный HTTP-получатель дал три попытки и одно сообщение
  в DLQ, итоговый `succeeded` сохранился.
- Ruff: проверка кода и форматирования.

## Ограничения и что осознанно не сделано

- Настоящий шлюз, отмены, возвраты, пользователи, UI, мониторинг и Kubernetes
  отсутствуют: этого нет в ТЗ. У реального шлюза нужен собственный идемпотентный
  идентификатор операции на случай сбоя между списанием и коммитом БД.
- Нет автоматической очистки outbox/ключей и административного повтора DLQ:
  сначала нужна политика хранения и ручного разбора. Просмотр доступен через
  RabbitMQ Management. При трёх технических сбоях до получения исхода платёж
  может остаться `pending`, а событие будет в DLQ.
- Нет HMAC-подписи webhook и ограничений на приватные адреса назначения:
  локальные HTTP-адреса нужны для демонстрации. Решение рассчитано на доверенного
  владельца статического API key, не на публичный приём произвольных URL.
- Один узел RabbitMQ и один PostgreSQL не обеспечивают доступность при потере
  диска/узла. Гарантии здесь относятся к временным сбоям, подтверждениям и
  рестартам с сохранением данных. Нагрузочные и хаос-тесты кластера не выполнялись.
- Тестовые зависимости включены в один образ: проверка выполняется тем же
  окружением, что приложение. Отдельный production-образ для этого задания
  не добавлялся.

## Что дальше при расширении задачи

1. Согласовать протокол настоящего шлюза, дедупликацию и подпись webhook.
2. Определить хранение истории и безопасный ручной повтор событий из DLQ.
3. После появления SLA измерить нагрузку и решить, нужны ли параллельные
   обработчики, отдельный relay, метрики и отказоустойчивая инфраструктура.

Технические источники: [подтверждения RabbitMQ](https://www.rabbitmq.com/docs/confirms),
[prefetch FastStream](https://faststream.ag2.ai/latest/rabbit/prefetch/),
[quorum queues и DLQ](https://www.rabbitmq.com/docs/quorum-queues).
Поведение проверено на версиях из `requirements.lock`, а не только по документации.
