# План до реализации

Источник: `задание.pdf`, четыре страницы. Разбор требований и семь рабочих
допущений выполнены до написания кода; итоговые контракты будут в README.

## Минимальная архитектура

- API пишет payment и outbox в одной транзакции PostgreSQL.
- В процессе consumer фоновая задача публикует готовые записи outbox в RabbitMQ.
- Один обработчик сохраняет результат эмуляции, затем отправляет webhook.
- При ошибке попытка атомарно закрывается вместе с созданием записи следующей
  попытки либо DLQ. Задержка хранится в outbox.available_at и переживает рестарт.
- ACK только после коммита. Publisher confirms + mandatory + persistent messages.
- Обработанные outbox-записи служат также квитанциями от повторной доставки.

3. Реализовать обработку, outbox, устойчивые повторы и DLQ.

## Осознанно вне объёма

Нет настоящего шлюза, возвратов, пользователей, UI, метрик, DI-контейнера,
универсальных репозиториев и нескольких обработчиков: ТЗ этого не требует.
Нет exactly-once для внешнего HTTP: потеря ответа допускает дубликат webhook.
Нет административного API повторного запуска DLQ или очистки истории: сначала
нужна политика хранения и повторной обработки. Локальный webhook допускается
для тестового окружения; публичный многопользовательский сервис требует
отдельной политики исходящих сетевых запросов.
